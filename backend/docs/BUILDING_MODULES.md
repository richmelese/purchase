# Backend module conventions

Read this before writing any module. The foundation below already exists and is stable — build
on it, don't reinvent it, and don't edit the shared files listed under "Hands off" (report back
instead; the coordinator wires those up centrally to avoid merge races between parallel agents).

## Stack

NestJS 11 (Express), TypeScript, `node:sqlite` (`DatabaseSync`, synchronous — no async DB calls,
no migrations framework, just `CREATE TABLE IF NOT EXISTS` in `src/db/schema.ts`). No ORM.

## Reference module

Read `src/modules/auth/*` first — it's the canonical example of controller/service/module shape,
error conventions, and how guards attach `req.user`.

## Already built — use, don't duplicate

- **`src/db/database.service.ts`** (`DatabaseService`, globally injectable): `.get<T>(sql, params)`,
  `.all<T>(sql, params)`, `.run(sql, params)` (params: positional array `[a, b]` with `?` placeholders
  — always use this form, not named params), `.transaction(fn)` for multi-statement writes.
- **`src/db/schema.ts`** — the complete schema (all tables already exist: `users`, `roles`,
  `user_party_rights`, `sessions`, `parties`, `products`, `invoices`, `invoice_lines`, `payments`,
  `stock_issues`, `settings`, `lookup_values`, `vat_adjustments`, `bank_accounts`,
  `bank_transactions`, `activity_log`). **Do not edit this file.** If you believe a column is
  genuinely missing, say so in your final report instead of changing it — don't risk clobbering
  another agent's concurrent edit.
- **`src/common/calc.ts`** — `computeLine(line, rules)`, `computeTotals(lines)`,
  `computeWithholding(inv, rules)`, plus the constant lists (`UNITS`, `PURCHASE_TYPES`,
  `SALES_TYPES`, `RECEIPT_PREFIX`, `receiptNumberError`, etc.). This is a byte-for-byte port of the
  frontend's tax math — use it for ANY VAT/withholding/line-total calculation, never recompute by hand.
- **`src/common/ethiopian.ts`** — `taxPeriod(iso)` → `{fy, idx, month, ecYear}`, `toEthiopian`,
  `toGregorian`, `FY_MONTHS`, `fiscalYearLabel`, `periodRange(fy, idx)`. Use `taxPeriod(date).fy` /
  `.idx` for every invoice's stored `fy`/`fy_month`.
- **`src/common/permissions.ts`** — `RESOURCES`, `RIGHTS`, `can(user, resource, right, task?)`,
  `canCompany(user, partyId, right)`. `req.user` (once `AuthGuard` runs) already has `role`,
  `permissions`, `access_all_parties`, `party_rights` populated — call `can()`/`canCompany()`
  directly on it, don't re-derive.
- **`src/common/auth.guard.ts`** (`AuthGuard`) — put `@UseGuards(AuthGuard)` on every controller
  that requires sign-in (i.e. everything except `/api/auth/status|signup|login`). It populates
  `req.user` (type `AuthUser` from that file) and throws 401 if not signed in.
- **`src/common/require-permission.decorator.ts`** — `@RequirePermission('purchases', 'edit', 'update_purchase')`
  on a route handler enforces that grant (throws 403) after `AuthGuard` has run. Stack both:
  `@UseGuards(AuthGuard) @RequirePermission(...)` on the handler, or guard the controller and
  decorate individual handlers for the permission.
- **`src/common/current-user.decorator.ts`** — `@CurrentUser() user: AuthUser` param decorator.
- **`src/common/activity-log.ts`** — `logActivity(db, user, action, entity, entityId, summary)` —
  call this on every create/update/delete. `action` is `'create'|'update'|'delete'|'other'`.
  `AUDIT_ENTITIES` is the catalog for `GET /api/audit/entities`.
- **`src/common/password.ts`** — `hashPassword`/`verifyPassword`/`randomPassword` (scrypt).
- **`src/common/http-exception.filter.ts`** — already global. Throw Nest's `BadRequestException`,
  `NotFoundException`, `ForbiddenException`, etc. For field-level form errors, throw
  `new BadRequestException({ error: 'Please check the form', fields: { tin: 'Required' } })` — the
  filter turns that into `{ error, fields }` JSON, which is exactly what `frontend/lib/api.js`
  expects (it reads `data.error` and `data.fields`).

## Conventions to follow

- **Routes**: `@Controller('api/<area>')`, matching `docs/API_CONTRACT.md` paths EXACTLY (the
  frontend proxies the full `/api/...` path verbatim — no prefix stripping).
- **Response shapes**: match `docs/API_CONTRACT.md` field-for-field. The frontend was already
  built against this contract and will not be touched — any mismatch is a silent runtime bug, not
  a type error.
- **204 responses**: `@HttpCode(204)` and return nothing (`undefined`) for plain deletes, per the
  contract (note: a couple of endpoints deliberately return a body instead of 204 — e.g.
  `DELETE /api/users/:id` returns the full updated user list; check the contract for each route).
- **Computed/derived fields** (invoice totals, withholding, stock levels, aging buckets) are
  **never stored** — compute them at read time from `calc.ts`/`ethiopian.ts` plus the raw rows, so
  they always reflect the current tax rules in `settings`. Read `vat_rate`/`wh_rate`/thresholds
  from the `settings` table (id=1) and pass them as the `rules` argument to `computeLine` /
  `computeTotals` / `computeWithholding` — never hardcode `0.15`/`0.03`.
  **Important**: `computeWithholding` and the `calc.ts` types use **fractions** (`0.15`), but the
  `PUT /api/settings` wire format is also fractions per the contract — stay consistent, don't
  convert to percentages anywhere in storage.
- **Numbering** (`invoice_no` like `P0007`, `issue_no`): zero-pad to 4 digits, scoped by kind
  (`P`/`S`) — `SELECT COUNT(*) FROM invoices WHERE kind = ?` + 1, formatted `${kind}${String(n).padStart(4,'0')}`.
  Don't assume IDs are gap-free; compute "next" from the max existing numeric suffix, not row count,
  so a deleted invoice doesn't produce a duplicate number.
- **party_id resolution**: when a header carries `party_tin`, look up `parties` by `tin`; if found,
  set `party_id` and keep `party_name` in sync with the party's current name; if the TIN is new and
  non-empty, auto-insert a new `parties` row (type inferred from context — Supplier for purchases,
  Customer for sales, or `Both` if the TIN already exists as the other type) and use its id.
- **Company-level authorization**: for any read/write on a specific invoice/party, after the
  resource-level `can()` check, also call `canCompany(user, record.party_id, right)` — a
  non-admin, non-"all parties" user only reaches records for parties they were explicitly granted.
- **Dates**: always store/compare as Gregorian ISO (`YYYY-MM-DD`). `calendar_type` is display-only.
- **Money**: use `calc.ts`'s `round2` for anything derived; SQLite `REAL` columns are fine for raw
  inputs (qty, unit_price, etc.).
- **Validation errors**: field keys are dotted paths for nested shapes (e.g. `profile.general.tin`)
  or `line_items.<index>.<field>` for invoice lines — match the contract's examples.

## Hands off (coordinator-owned, to avoid multi-agent write races)

- `src/app.module.ts` — don't edit. In your final report, state the exact import line and the
  `imports: [...]` entry your module needs (e.g. `import { PartiesModule } from './modules/parties/parties.module'; PartiesModule`).
- `src/db/schema.ts` — don't edit (see above).
- Any other module's folder under `src/modules/` — stay inside your own.

## Testing your work

The dev server runs via `npm run dev` from `backend/` (hot reload) or you can boot it directly for
a quick smoke test: `DATABASE_PATH=data/dev-test.db PORT=5000 HOST=127.0.0.1 node -r ts-node/register src/main.ts`
(use a throwaway `DATABASE_PATH` so you don't collide with other agents' test runs against the
same file). Sign up a user first (`POST /api/auth/status` then `/api/auth/signup` — first signup
is `role: admin`), `POST /api/auth/login`, keep the cookie (`curl -c/-b cookies.txt`), then hit
your new endpoints. `BFF_SHARED_SECRET` is unset in dev so the `x-bff-secret` guard is a no-op.
